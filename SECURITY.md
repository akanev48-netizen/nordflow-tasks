# Отчёт по безопасности NordFlow Tasks

## Уровень риска: 🔴 КРИТИЧНЫЙ

Приложение не имеет серверной части. Вся логика и данные хранятся в `localStorage` браузера. Это фундаментальное ограничение, которое делает приложение **непригодным для реального использования** с конфиденциальными данными.

---

## 🔴 КРИТИЧНЫЕ уязвимости

### 1. Пароли хранятся открытым текстом
**Файл:** `src/seed.ts:18-25`, `src/api.ts:43`

Все пароли (`123456`) хранятся в `localStorage` без хеширования. Любой может:
- Открыть DevTools → Application → localStorage
- Увидеть пароли всех пользователей

```js
// seed.ts — пароль открытым текстом
{ id: 'u1', email: 'volkova@nordflow.ru', password: '123456', ... }
```

### 2. Подмена пользователя (Identity Spoofing)
**Файл:** `src/api.ts:44-46`

Текущий пользователь определяется только по `localStorage`:
```js
localStorage.setItem(KEYS.currentUser, user.id);
```
Любой может:
- Открыть DevTools
- Изменить `ndf_current_user` на `u1` (admin)
- Получить полный доступ администратора

### 3. Подмена роли (Role Escalation)
**Файл:** `src/api.ts:69-76`

Роли хранятся в `localStorage`. Любой сотрудник может:
```js
// В DevTools:
let users = JSON.parse(localStorage.getItem('ndf_users'));
users[0].role = 'admin'; // назначить себе роль админа
localStorage.setItem('ndf_users', JSON.stringify(users));
```

### 4. Все данные доступны через DevTools
**Файл:** `src/api.ts:15-22`

Вся база данных (пользователи, задачи, пароли) доступна для:
- Просмотра
- Изменения
- Удаления
- Экспорта

## 🟠 ВЫСОКИЕ уязвимости

### 5. Нет проверки роли на странице AdminUsers
**Файл:** `src/pages/AdminUsers.tsx`

Страница управления пользователями не проверяет роль текущего пользователя. Хотя ссылка скрыта в боковом меню, прямой переход по URL откроет страницу.

### 6. XSS не защищён через подстановку в HTML
**Файл:** `src/pages/TaskPage.tsx:149`

Значения из истории (`h.oldValue`, `h.newValue`, `h.field`) вставляются в JSX без экранирования. React экранирует автоматически, но если появится `dangerouslySetInnerHTML` — это станет XSS.

### 7. Нет ограничения попыток входа
**Файл:** `src/api.ts:41-49`

Нет rate limiting на вход. Можно перебирать пароли бесконечно.

## 🟡 СРЕДНИЕ уязвимости

### 8. Токен GitHub в истории git
GitHub-токен (`ghp_...`) был встроен в URL репозитория при пуше. Хотя URL был изменён, токен может остаться в истории git-коммитов.

### 9. Данные не зашифрованы
Все данные в `localStorage` хранятся в открытом формате JSON без шифрования.

### 10. Нет сессий и таймаутов
Сессия не истекает. Если пользователь не нажал «Выйти», он остаётся залогиненным навсегда (в пределах браузера).

### 11. Демо-данные видны на странице входа
**Файл:** `src/pages/Login.tsx:58-60`

На странице входа написано: «Используйте любую электронную почту / пароль: 123456».

## 🟢 НИЗКИЕ уязвимости / защищено

- ✅ **XSS через React** — React экранирует JSX по умолчанию, прямых инъекций нет
- ✅ **Нет серверных инъекций** — нет SQL, нет backend API
- ✅ **Confirm диалоги** — критические действия требуют подтверждения
- ✅ **Клиентский RBAC** — визуально скрыты кнопки для неавторизованных ролей

## Рекомендации

### Должная (Must Have) для реального использования:
1. **Серверная часть** (Node.js, Supabase, Firebase) для хранения данных и авторизации
2. **Хеширование паролей** (bcrypt) на сервере
3. **JWT-токены** с refresh-механизмом
4. **Серверная проверка ролей** на каждом API-эндпоинте
5. **Rate limiting** на эндпоинте входа

### Для демо-версии (рекомендуется):
6. Убрать отображение пароля на странице входа
7. Добавить проверку роли в `AdminUsers.tsx`
8. Убрать пароли из seed-данных (или захешировать)
9. Ротировать GitHub-токен
